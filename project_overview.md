# Cross-Platform OpenGL Overlay Library – First Pass Design

&#x20;*Example of a cross-platform transparent overlay window (Sciter sample) on macOS (left), Ubuntu Linux (center), and Windows (right). The window is borderless, always-on-top, and uses per-pixel transparency so that the desktop (or underlying app) is visible through transparent areas.*

## Overview

We propose a **native overlay library** (Apache 2.0 licensed) that creates a transparent OpenGL-rendered window aligned with a target HTML element in a React-based app. The overlay will support **Windows 10+**, **macOS 11+**, and **Ubuntu 20.04+** (X11 composited desktop), providing a synchronized visual layer on top of the specified HTML element. Key requirements and features include:

* **Per-Pixel Transparency:** The overlay window will have an alpha channel, so it can blend with the underlying application content. Only the graphics we draw (e.g. highlights or annotations) will be opaque; all other areas will be fully transparent, allowing the underlying React app to show through.
* **Always-On-Top, No Decorations:** The overlay is a borderless, decoration-free window kept above the main application window. This ensures the overlay perfectly covers the target HTML element without OS chrome or dropping behind other windows.
* **Input Pass-Through:** User input (mouse clicks, etc.) should be handled by the React app as usual. The overlay will be configured to ignore input in its transparent areas so that clicks "fall through" to the underlying UI. This keeps overlay visuals and React interactivity in sync.
* **Integration with React:** The React layer (front-end) will inform the native overlay of the target element’s screen position and size. The overlay window will be moved and resized accordingly to **exactly coincide** with the HTML element, keeping any visuals in the overlay aligned with the underlying content. If the element moves (e.g. due to layout changes or scrolling), the overlay is updated to match.
* **OpenGL Rendering:** The overlay uses hardware-accelerated OpenGL for drawing. This could be used for custom effects, highlighting, or rendering content at high performance. We will set up an OpenGL context for the overlay window on each platform. The rendering can be as simple as drawing an textured quad or lines, depending on the app’s needs. We ensure the OpenGL context includes an alpha channel (RGBA) so that clearing the screen with alpha=0 yields transparency.
* **Build and Distribution:** The library will be built as a Node.js native addon (in C/C++), using **CMake** as the build system for cross-platform support. We will package precompiled binaries for major OSes using **prebuildify**, so that developers can install the npm package without needing to compile locally. The delivered package will include binaries for Windows, macOS, and Linux (matching the OS versions/ABIs mentioned), under the Apache-2.0 license.

Below we detail the platform-specific implementation and then outline the overall architecture and steps for a first-pass implementation.

## Platform-Specific Implementation Details

### Windows 10+ (Win32 with DWM)

On Windows, we leverage the Desktop Window Manager (DWM) composition (available on Vista and later, which includes Windows 10+) to create a transparent, click-through overlay window:

* **Window Creation:** We create a top-level window with **no border or titlebar**. This is achieved by removing the standard overlapped window style and using `WS_POPUP` style, along with extended styles for transparency. The window is also created with `WS_EX_TOPMOST` (or set with `SetWindowPos(..., HWND_TOPMOST, ...)`) so it stays above the browser window. We likely also use `WS_EX_TOOLWINDOW` to avoid showing in the taskbar/Alt-Tab, since the overlay is an auxiliary window.
* **Transparency via DWM:** To enable per-pixel transparency, the overlay window will use the DWM blur-behind feature. We call `DwmEnableBlurBehindWindow(hWnd, &bb)` with `bb.fEnable = TRUE` to tell DWM to treat our window’s background as blurred/transparent. By specifying an *empty blur region* (or a 1x1 pixel region), we effectively make the entire window fully transparent except for drawn content. In practice, that means we set `bb.hRgnBlur = CreateRectRgn(0,0,1,1)` and `bb.dwFlags = DWM_BB_ENABLE | DWM_BB_BLURREGION` as suggested by community examples. This avoids the semi-transparent “Aero glass” effect and instead makes the window genuinely transparent wherever we don’t draw anything.
* **OpenGL Context:** We create an OpenGL rendering context for the window (using WGL). When choosing a pixel format for the window’s HDC, we request an RGBA format with an alpha channel (e.g. 32-bit color with alpha). This, combined with DWM composition, allows the alpha channel to make the window areas translucent. In our render loop, we call `glClearColor(0,0,0,0)` (alpha=0) and clear the color buffer to ensure the background is transparent. Anything we then draw with alpha (blending enabled) will appear over the underlying content.
* **Input Handling:** The overlay window should **not intercept mouse/keyboard events**. On Windows, we achieve this by using the extended style `WS_EX_TRANSPARENT` on the overlay window. This flag causes mouse events to **fall through** the window, so clicks go to whatever is underneath. (Internally, Windows will act as if the overlay isn’t there for hit-testing, except for any fully opaque pixels if we used colorkey transparency – but here we use per-pixel alpha.) We will combine `WS_EX_TRANSPARENT` with `WS_EX_LAYERED` (required for per-pixel transparency on older mechanisms). With DWM, this setup ensures the user can interact with the React app under the overlay as normal, even if the overlay is present. We also consider using `WS_EX_NOACTIVATE` so that the overlay window never takes focus away from the main window if somehow clicked.
* **Position & Sync:** We can position the overlay by using `SetWindowPos` to the exact coordinates of the target HTML element. Windows coordinates are in screen space, so we will obtain the element’s screen position (likely via the React app invoking a native method with the bounding box). Whenever the element moves or changes size, we call `SetWindowPos`/`MoveWindow` on the overlay to keep it aligned.

**Windows Summary:** In effect, the Windows overlay is a **layered OpenGL window** with composition enabled. This is a known approach to get OpenGL content with a transparent background. With DWM (always on in Win10) handling the composition, the overlay can blend over the browser. And by marking it transparent to input, we ensure the overlay is visually present but functionally invisible to interaction (all events go to the underlying app).

### macOS 11+ (Cocoa)

On macOS, we create a borderless NSWindow with an OpenGL context, using Cocoa APIs to achieve a transparent, non-interfering overlay:

* **Window Creation:** We use an `NSWindow` with **NSWindowStyleMaskBorderless** (no title bar or border) so it can freely float above the app content. We also set the window level to **NSFloatingWindowLevel** (equivalent to always-on-top) so it stays above the browser window. The window is given a transparent background. In Cocoa, that means setting `[window setOpaque:NO]` and `[window setBackgroundColor:[NSColor clearColor]]`. This instructs the compositing system that the window may have transparent regions. We also ensure the content view doesn’t draw an opaque background.
* **OpenGL Context:** We attach an NSOpenGLContext (or use a modern GLKit view, though OpenGL is deprecated on macOS – we stick with it as required). By default, an `NSOpenGLView` returns `isOpaque=YES`, which would prevent transparency. To override this, we can either subclass or category-patch NSOpenGLView to return NO for `isOpaque`, or simply not use NSOpenGLView and instead create a custom NSView and manually create an NSOpenGLContext. In either case, we must ensure the OpenGL surface has an alpha channel. We can do this by setting NSOpenGLPixelFormatAttribute with kCGLPFADoubleBuffer, kCGLPFAColorSize 32, kCGLPFAAlphaSize 8, etc. Once the context is set up, we make it clear the buffer with an alpha 0 clear color just like on Windows. Cocoa’s compositor will then blend our window pixels with the windows behind it.
* **Transparency & Input:** On macOS, an interesting behavior is that **borderless windows automatically support click-through on transparent areas** by default (the system will pass clicks to windows behind if the top window’s region is clear). We must be careful *not* to disable this. In particular, we should **avoid calling** `[window setIgnoresMouseEvents:NO]` on a borderless window, because that can disturb the default click-through state. We also should not make the content view layer-backed in a way that breaks this (older macOS versions had issues if `wantsLayer=YES`, though in recent macOS the behavior might be better). Essentially, by creating a borderless, non-opaque window and drawing with transparent OpenGL, any clicks on transparent parts of the window will fall through to whatever is underneath – which is exactly what we want. This behavior is documented in Apple’s examples (e.g., the *Round Transparent Window* sample shows how an NSWindow with holes allows click-through on those holes). Our overlay window will only have “solid” (opaque) pixels where we draw something; all other areas are clear and will not block mouse events to the browser.
* **Position & Sync:** We will use `[window setFrame:frame display:YES]` to position the NSWindow over the target element’s screen coordinates. (In an Electron context we might get the global screen coordinates via a JS call, or if the React app is inside a native WebView, we have ways to translate coordinates.) The overlay NSWindow can be made **key or non-key**; ideally it should not steal focus. By default, an NSBorderlessWindowLevel window won’t become key unless clicked; if we have click-through everywhere except perhaps drawn shapes, it likely never becomes key. We can also call `[window setLevel:NSFloatingWindowLevel]` and possibly `[window setCollectionBehavior:NSWindowCollectionBehaviorCanJoinAllSpaces]` if we want it to appear even across Spaces (if needed). The overlay NSWindow will track element movements by updating its frame as needed.

**macOS Summary:** The macOS overlay is an always-on-top NSWindow with a transparent OpenGL layer. We leverage Cocoa’s compositing: by marking the window non-opaque and clearing with transparent color, the window’s background shows whatever is behind it. Critically, because we leave the default behavior intact for borderless transparent windows, mouse events in transparent regions go to underlying views (our React app). The result is an overlay that visually augments the interface without breaking normal UI interactions.

### Ubuntu 20.04+ (Linux X11)

On Linux, we target X11 with a compositing window manager (which is the default in modern Ubuntu desktops like GNOME). The overlay window will be an undecorated X11 window with an ARGB visual and an OpenGL context (likely via GLX or EGL):

* **Window Creation:** Using Xlib/GLX, we create an X11 window with a 32-bit RGBA visual (depth 32). We need to ensure the selected X visual has an alpha channel in its format. For example, on X11 we query for an FBConfig that supports an alpha buffer. Many X11 visuals can be 32-bit but not actually use the alpha bits; to avoid that, one can verify the visual's XRenderPictFormat has an alpha mask. Libraries like GLFW or SDL can handle this selection internally. We will likely use the GLX extension `GLX_RGBA_BIT` with alpha or simply use `glfwWindowHint(GLFW_TRANSPARENT_FRAMEBUFFER, GLFW_TRUE)` if we leverage GLFW (which under the hood requests an RGBA visual).
* **Compositing:** A compositing window manager is required for transparency. In Ubuntu 20.04, the default GNOME Shell is a compositor, so ARGB windows will be composited with the background. (If someone ran a non-compositing X11 session, the transparent window would not blend and would just appear black where transparent – but such environments are uncommon for our target base.) We may document that **compositing must be enabled**, similar to how NW\.js notes transparency support requires compositing. In our code, after creating the X11 window, we map it with an event mask for exposure, etc. We then use GLX to create a context and make it current on that window. Clearing with glClearColor(0,0,0,0) will leave those pixels transparent in the composited output.
* **OpenGL Context:** We can use GLX (since Ubuntu 20.04 primarily uses X11; Wayland is optional in 20.04 but we will target X11 first). We choose an FBConfig with `GLX_ALPHA_SIZE >= 8`. Then create a context (likely an OpenGL 3.x context for modern features, falling back to 2.1 if needed for compatibility). We then render the same way: clear to transparent, draw overlay visuals. If we use a library like GLFW: it simplifies much of this, as we can do `glfwWindowHint(GLFW_DECORATED, GLFW_FALSE)` for no border and `glfwWindowHint(GLFW_TRANSPARENT_FRAMEBUFFER, GLFW_TRUE)` for alpha. GLFW will also handle creating a GL context. We would still need to ensure the window is always on top; GLFW doesn’t implicitly do that on X11 unless we set `GLFW_FLOATING`, which corresponds to asking the window manager to keep it above others.
* **Always-on-Top:** On X11, to keep the window on top, we set the `_NET_WM_STATE_ABOVE` hint or use an override-redirect window. Since this is a utility overlay, we might use an override-redirect window (which bypasses the window manager for stacking and positioning). However, using override-redirect means we have to manage moving it on our own and it won’t appear in task switcher (which is fine). Alternatively, we can create a normal window and use an X11 API or EWMH message to set it as "above". Many toolkits (and GLFW’s floating hint) internally set the appropriate hint to request always-on-top. We will ensure the overlay window is created as non-user-interactive and above the main window’s XID in stacking order.
* **Input Handling:** To make the overlay click-through on X11, we utilize the **X11 Shape extension** on the *input* region. The X Shape extension allows us to define both a visible shape and an *input shape* for the window. We will set the input shape to an empty region, effectively telling X11 that our window does not accept any input anywhere. In code, this is done with something like: `XFixesCreateRegion` (an empty region) and `XFixesSetWindowShapeRegion(display, window, ShapeInput, 0, 0, region)`. By doing so, all mouse clicks and keyboard events pass right through our overlay window to whatever is behind it (the browser). This is analogous to WS\_EX\_TRANSPARENT on Windows. Another approach could be to track where we draw opaque content and set the input shape only to those pixels, but in our case we likely want no input at all to be captured by the overlay. We will also make sure the window is **non-focusable**. (If using override-redirect, it never gets focus by design. If not, we can set WM\_HINTS input=False or use XSetInputFocus appropriately.)
* **Position & Sync:** Converting the target element’s position to X11 screen coordinates requires knowing the window position of the browser and the element’s offset within it. If the React app is running in a standard web browser, an external method is needed (perhaps an accessibility API or a browser extension can provide the element’s global coordinates). In an integrated app scenario (like Electron or a controlled environment), the React code can communicate the coordinates to the Node addon. We will then position the X11 window via `XMoveResizeWindow` accordingly. Because override-redirect windows do not have a window manager frame, their position is straightforward to set relative to the root window (screen). We also handle resizing the overlay window if the target element’s size changes, using `XResizeWindow` as needed.

**Linux Summary:** The Linux overlay is achieved with an ARGB X11 window that uses the Shape extension for input pass-through and relies on the compositing manager to blend OpenGL-drawn content with the underlying application. We must ensure an appropriate visual with alpha is chosen. Modern frameworks (e.g., Chromium Embedding in NW\.js) use flags like `--enable-transparent-visuals` for this purpose – our implementation mirrors that by requesting a transparent framebuffer. With the window properly shaped for input, the React app beneath remains interactive, and the overlay simply draws on top, synchronized to the element’s position.

### Note on Wayland (Linux)

*(While Ubuntu 20.04 defaults to X11, future Linux environments use Wayland by default. A Wayland-compatible overlay would require a different approach, as Wayland does not allow an arbitrary global always-on-top window in the same way X11 does. It might require using a Wayland protocol like Layer Shell or abusing subsurfaces in a specific compositor. For now, our first implementation is X11-only. Advanced Wayland support can be explored later.)*

## Implementation Outline (First Pass)

With the platform-specific concepts established, we outline a **first-pass implementation** of the library. The development will be in C/C++ as a Node.js addon, with a thin JavaScript API for the React app to use. We focus on getting a basic working overlay on each OS:

1. **Project Setup:** Use CMake to organize the build for multiple platforms. We define a core C++ source that uses **Node-API** (N-API) or **node-addon-api** for creating the addon. The CMakeLists will detect the platform and link against the required system libraries (e.g., *opengl32.lib*, *dwmapi.lib* on Windows; *Cocoa.framework*, *OpenGL.framework* on Mac; *X11*, *Xext*, *Xfixes*, *GL*, *GLX* on Linux). We will also include any needed headers for each platform (Win32 API, Cocoa Objective-C code in an `.mm` file, Xlib, etc.). The output will be a compiled binary (`.node` module) that can be required in Node. Using **prebuildify**, we will compile these for each target OS/architecture and bundle them. (This means the npm package includes `*.node` binaries for Windows x64, macOS x64/arm64, Linux x64, etc., making installation seamless for users without build tools.)

2. **Node.js Addon API Design:** Expose a simple JavaScript interface to control the overlay. For example, the addon might provide:

   * `createOverlay(id, x, y, width, height)` – creates an overlay (or reuses one) for a given DOM element identified by `id` or by direct coordinates. In a minimal implementation, we might not pass `id` but directly the coordinates from React.
   * `updateOverlay(id, x, y, width, height)` – repositions/resizes the overlay (to be called when the target element moves or changes size).
   * `destroyOverlay(id)` – destroys the overlay window.
   * Possibly methods to draw or update content in the overlay (e.g., `drawImage(id, imageData)` or `drawHighlight(id, shape)`), or we might handle the drawing internally based on some state.

   The addon will maintain references to the created native windows/contexts in a data structure (probably mapping an overlay ID to native window info).

3. **Creating the Overlay Window (Native Code):** When `createOverlay` is called (with initial coordinates), the native code will:

   * Initialize any library needed (for instance, if using GLFW, call `glfwInit()`; if not, ensure OS-specific initializations are done. On macOS, we might need to start an `NSApplication` if not already running – possibly using `NSApp = [NSApplication sharedApplication]` and `[NSApp activateIgnoringOtherApps:YES]` without opening a menu).
   * Create the window in a platform-specific way:

     * **Windows:** Call `CreateWindowEx` with styles as discussed (`WS_POPUP|WS_EX_LAYERED|WS_EX_TRANSPARENT|WS_EX_TOPMOST|WS_EX_TOOLWINDOW`). We then obtain an HDC and set up Pixel Format Descriptor with alpha. Create an OpenGL context via `wglCreateContext`. Call `DwmEnableBlurBehindWindow` to enable transparency (with blur region hack for full transparency). Also call `SetLayeredWindowAttributes` if needed (to ensure the whole window uses per-pixel alpha). Finally, show the window (ShowWindow) and position it with MoveWindow to (x,y,width,height).
     * **macOS:** In an Objective-C section, create an `NSWindow` with `initWithContentRect:NSMakeRect(x,y,w,h) styleMask:NSWindowStyleMaskBorderless backing:NSBackingStoreBuffered defer:NO`. Set its level to NSFloatingWindowLevel. Create an NSOpenGLPixelFormat with alpha, NSOpenGLContext, and attach to window’s content view. Mark window as opaque=NO, backgroundColor clear. Call `[window makeKeyAndOrderFront:nil]` (or just orderFront since we may not want it key). The coordinate (x,y) we receive likely needs conversion from top-left to Cocoa’s coordinate system (flipped y). We handle that so it aligns over the element. We ensure the window ignores nothing (so it will allow click-through by default for transparent parts).
     * **Linux (X11):** Open a connection to X11 (`XOpenDisplay`). Choose a 32-bit visual (using X11/Xrender queries or GLXFBConfig). Create an X window with `XCreateWindow` (CWColormap, etc.) using that visual. Set WM hints for bypassing window manager if needed (or use override-redirect = True in XSetWindowAttributes for simplicity). Map the window. Use GLX to create context and make current. Also call XFixesSetWindowShapeRegion to set an empty input region. Position the window with XMoveResizeWindow to (x,y,w,h). If not override-redirect, also send `_NET_WM_STATE_ABOVE` message to keep it on top.
   * After creation, also initialize any needed data for rendering (e.g., load OpenGL functions via GLAD/GLEW if needed, set glViewport, etc.).

4. **Rendering Loop:** For a first implementation, we can keep the rendering simple. If the overlay content is mostly static (e.g., highlighting an element), we might draw once and then only redraw when needed. If dynamic (e.g., some animation or frequently updating overlay), we need a continuous render loop. We have a few choices:

   * Use a separate thread to run a rendering loop (especially if we want to use `glfwPollEvents()` or process OS events continuously without blocking Node).
   * Use the Node event loop (UV) to schedule periodic redraws or event processing.

   A safe approach is to create a dedicated thread for each overlay window (or one thread that manages all overlay windows) that handles OS event polling and rendering. For example, on X11 we need to `XNextEvent` to handle expose events; on Windows, we need a message loop (`GetMessage/DispatchMessage`) for the window; on macOS, we might rely on the Cocoa runloop. Running those in the Node main thread would block JS, so a separate thread is preferred. The thread can periodically render frames (or render on-demand). We will likely:

   * Signal the thread when there’s something to draw or when the overlay needs to update.
   * Use OpenGL calls to render whatever is needed (for a simple highlight, maybe draw a translucent rectangle or texture).
   * Swap buffers (glSwapBuffers or equivalent) to display the frame.
   * Sleep or wait for next update.

   For the first pass, we might not need a high-framerate loop – just render once and update if triggered. For example, if the overlay is highlighting an element with a border, it only needs re-draw if the highlight effect changes.

5. **Synchronization with React App:** The React app (in the browser/Electron) will know when the target element moves, resizes, or needs an overlay update. We will provide a mechanism (perhaps a tiny JS module that uses the addon) for the React app to call e.g. `updateOverlay(id, newX, newY, newWidth, newHeight)` on window resize or scroll. That call will invoke a native function which adjusts the native window position/size accordingly. This keeps the overlay *locked* on the element. If multiple overlays are needed for multiple elements, the app can create multiple overlays (each with its own id or handle).

6. **Cleanup:** Implement `destroyOverlay` to tear down the overlay window and OpenGL context when no longer needed (e.g., if the overlay should be removed). This will destroy the native window (DestroyWindow on Win32, `[window close]` on Cocoa, XDestroyWindow on X11), release the GL context and any allocated resources. Also stop any threads associated with it. This ensures we don’t leak OS resources.

7. **Testing on All Platforms:** We will test the first pass on Windows 10, macOS 11 (Big Sur or later), and Ubuntu 20.04 (with default GNOME). The expected result is an overlay that can draw something (for test purposes, maybe fill with a semi-transparent color or draw a border) exactly over a known position. We will verify that:

   * The overlay aligns pixel-perfectly with the target element.
   * The background of the overlay is truly transparent (we see underlying app except where we draw).
   * Mouse clicks on the overlaid area still activate underlying buttons/inputs in the React app (proving our input transparency works).
   * No focus or window ordering issues (the overlay should not become the active window or steal keyboard focus when it appears).
   * Performance is good (no significant lag when moving the overlay or updating it).

8. **Using GLFW/Third-Party (optional):** As an alternative to writing low-level code for each platform in the first iteration, we could leverage a library like **GLFW** to simplify cross-platform window creation and context management. GLFW supports creating transparent frame buffer windows by simply setting a window hint, and can create borderless windows and set them floating (always on top). We could do something like: call `glfwInit(); glfwWindowHint(GLFW_TRANSPARENT_FRAMEBUFFER, GLFW_TRUE); glfwWindowHint(GLFW_DECORATED, GLFW_FALSE); glfwWindowHint(GLFW_FLOATING, GLFW_TRUE);` then `glfwCreateWindow(width, height, "")`. Once we have the `GLFWwindow`, we can retrieve the native window handle (glfwGetWin32Window / glfwGetCocoaWindow / glfwGetX11Window) to further adjust styles (like adding WS\_EX\_TRANSPARENT on Windows, or shaping input on X11). GLFW would manage the OpenGL context and basic event loop. This approach might speed up development. However, integrating GLFW with Node’s event loop and ensuring we can position the window precisely might require some tweaks. For the **first pass**, it’s acceptable to use GLFW as a dependency (its license is zlib/libpng, which is compatible with Apache 2.0). If GLFW proves cumbersome, we can implement platform-specific code as described above. The ultimate goal is a stable, flicker-free overlay window on all platforms.

## Building & Packaging with CMake and Prebuildify

Using **CMake** allows us to use a unified build configuration for Windows, macOS, and Linux, which is helpful for a cross-platform library. We will set up CMake to find OpenGL and OS-specific libraries. On Windows, we ensure it links against opengl32 and uses the Windows SDK for DWM functions; on macOS, we link the Cocoa and OpenGL frameworks; on Linux, link X11, Xfixes, etc. We can use [CMake.js](https://github.com/cmake-js/cmake-js) to integrate with Node’s build process if needed, or simply use a manual CMake invocation in our CI pipeline for each platform.

For distribution, **prebuildify** is chosen to ship precompiled binaries. This means when we publish to npm, we include the `.node` binaries in the package. The advantage is that end-users do not need to have compilers or build tools – installation is a simple download of the correct binary. We’ll configure our CI to run `prebuildify` for targets: Windows 64-bit (DLL for Node 16+/Electron etc.), macOS 64-bit (and arm64 if needed, since macOS 11 supports ARM Macs), and Linux x64 (glibc). The binaries will be built against Node-API (N-API) for maximal compatibility across Node versions. Since we’re using N-API, the binary can work on future Node versions without recompilation, further simplifying usage.

In summary, our build setup will ensure a developer can run `npm install overlay-lib` and get everything needed. Under the hood:

* The C++ code uses Node-API, so it is ABI-stable.
* We use prebuildify to package binaries, so `require('overlay-lib')` loads the native addon immediately with no compile step.
* The library is Apache 2.0 licensed, which we will indicate in package.json and in source headers. All third-party dependencies (if any, like GLFW or node-addon-api header) are permissively licensed as well, so the final distribution is compliant with Apache 2.0.
